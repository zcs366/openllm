# 品尝师四驾 · 迁钥

**日期**：2026-09-10
**作者**：军师（openLLM 品尝师 / 医师）
**对象**：`~/.openllm/config.json` 的明文 API key
**一句话**：`config.json` 里的三个明文 key 搬进了 Windows DPAPI 保护的密钥库；引擎在"配置里没有 key、环境变量也没有"的条件下连上 mimo 并被真模型回了一句「钥匙好使」。

---

## 一、这事是怎么被逼出来的

不是我想做安全，是**引擎自己每次启动都在喊**：

```
⚠️ config_keys: 以下provider有明文API key: deepseek, mimo, lmstudio
      → 建议改用环境变量 $ENV_VAR 引用
```

审计喊了很久，修法却一直是"改环境变量"——那只是把 key 从文件挪到 shell 历史里。今天把债务还掉：**迁进真正的凭据存储**。

---

## 二、侦查：WSL 里"真 keyring"到底有没有

先探再动，不然就是自欺。三条路的实测结果：

| 路 | 结果 | 判 |
|---|---|---|
| `keyring` 包 | 装上了（25.7.0），但挑中的后端是 `keyrings.alt.PlaintextKeyring` | **假安全**：base64 换个文件放，安全性 = 0。拒绝 |
| GNOME Keyring / SecretService | 系统里根本没装；装要 sudo（`sudo -n` 不通）且要跑 daemon | 走不通，且脆 |
| **Windows DPAPI**（`powershell.exe` 直调） | 往返探针成功，密文头 `01000000d08c9ddf…` = DPAPI 用户范围 blob | **通**，且是真加密 |

结论：**WSL 没有现成的真 keyring，那就给它接一个**——DPAPI 后端。这不是绕过，是把"系统凭据存储"这个语义在本机真正实现：密文由 **Windows 用户的登录凭据**派生保护，换机器、换 Windows 用户都解不开。

明文只走 stdin（不进 argv，不被 `ps` 看见）；落盘只有密文，0600。

## 三、五件交付

| # | 交付 | 文件 |
|---|---|---|
| 1 | 密钥库本体：三后端（keyring / dpapi / file）+ 取 key 顺序 | `src/openllm/security/keyvault.py`（新，~350 行） |
| 2 | 迁移脚本：写→读回校验→备份→摘明文→幂等 | `scripts/migrate_keys_to_vault.py`（新，可注入 vault 以便测试） |
| 3 | 引擎接线：六处取 key 点统一走 `engine_utils.get_api_key` | `core/engine.py`、`core/engine_utils.py` |
| 4 | 审计升级：明文清了还不够，**要盯后端安不安全** | `security/startup_audit.py` |
| 5 | 钉子 23 条 + 反证 | `tests/test_keyvault.py`（新，392 行） |

**取 key 顺序**（写进 docstring，不靠记忆）：环境变量 → 密钥库 → config.json 明文（兼容，但会打警告并指路迁移脚本）。

**为什么拒绝 PlaintextKeyring**：宁可降级到明说自己不安全的 `file` 后端，也不接受一个"看起来进了 keyring"的假安全。审计里那句 `无明文key，但密钥库后端不安全: file` 就是为它准备的。

迁移后 config.json：

```
deepseek   api_key=<无>  ref=keyvault
```

落盘：`~/.openllm/vault/{deepseek,mimo,lmstudio}_api_key.dpapi`，均 0600，内容为 DPAPI 密文。

### 4.2 引擎实调（`env -u MIMO_API_KEY -u DEEPSEEK_API_KEY`）

```
② 取 key 来源
   mimo      来源=keyvault:dpapi   ***len=51…v1si
   deepseek  来源=keyvault:dpapi   ***len=35…cc18
   lmstudio  来源=keyvault:dpapi   ***len=9…udio

③ 启动审计  [PASS] API key安全（密钥库: dpapi）

④ 真起引擎（不传 provider）
   provider = mimo | model = mimo-v2.5 | connected = True

⑤ 真说一句话（打真模型，验证 key 有效）
   模型回: 钥匙好使
```

**第 ⑤ 条是关键**：不是"连上了"这种自报，而是真 key 打真 API 拿回了模型的话。

## 六、边界与坦白

1. **DPAPI 绑人绑机**：密文只能在**同一个 Windows 用户、同一台机器**上解开。这是特性不是 bug（别人拷走 vault 文件也没用），但意味着——换机器要重新迁一次，且旧密文不可解。代码里那种情况会返回 None 并打警告，不会假装成功。
2. **`file` 后端不加密**：仅当 keyring 与 DPAPI 都不可用时才用（比如非 WSL 的 headless Linux）。它只解决"不摊在 config.json 里被备份/版本控制扫到"，**不解决安全**。审计会照喊。
3. **lmstudio 的 key 是占位串**（`lmstudio`，本地服务用哑 key），一并搬了——它被审计当成明文 key 在报警，搬走等于消掉一个假警报。副作用是好的：`else` 分支以前不管 provider 一律读 `DEEPSEEK_API_KEY`（对 lmstudio 是错的 key），现在统一走密钥库反而对了。
4. **gateway 的 key 没动**：它读 `~/one-api/.gateway_key` 独立文件，本就是分离的，不在本次范围。
5. **零 code 泄漏复查**：报告、卡片、日志、dry-run 输出里一律只出现 `mask()` 后的形态（`***len=51…v1si`）；连审计消息都断言了"不含 key 本体"（`test_audit_warns_on_plaintext_key`）。
