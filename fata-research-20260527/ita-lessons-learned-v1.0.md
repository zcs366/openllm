# ITA 运作经验总结

> ITA 是 openLLM 的前身实验。踩过的坑，就是 openLLM 要避的路。

---

## 一、ITA 做了什么

| 阶段 | 内容 | 结果 |
|------|------|------|
| 方案A | 传统 AST/CFG 编码 | 太重，放弃 |
| 方案B' | 纯 LLM 解码 | 0% 执行等价，解码器不够 |
| **方案C** | sBERT→DeepSeek 解码 | **60% 执行等价 + 100% 语法正确** |
| 红方审计 | 14 条声明审计 | 发现 3 个泡沫，砍掉 NCD/压缩率范式 |
| peer-review | 双模型同行评议 | v1.1.0 新增红方声明审计模式 |

**核心成果**：编码假设成立——代码行为可以被压缩为向量，解码后可恢复执行。

---

## 二、五条关键教训

### 教训 1：先哲学后行动，但不能永远哲学

ITA 花了大量时间在理论探讨（意图压缩四层论、信息论架构、Kolmogorov 复杂度），但代码实现滞后。

**经验**：哲学是必要的，但要有"截止日期"。想两周就该动手。不是想清楚再干，是**想得差不多就开始干，边干边想清楚**。

**对 openLLM 的启示**：协议已经写好（身份/记忆/技能/约束），下一步是写代码。不能再拖。

### 教训 2：五人合议有价值但要控制时长

五人合议（子产/韩信/鲁班/萧何/子贡）产出了高质量的决策，但每次合议耗时 20-40 分钟，多次合议积累下来消耗了大量资源。

**经验**：合议适合重大决策，不适合日常执行。日常用"两人对话"就够了。

**对 openLLM 的启示**：openLLM 的日常开发用"军师+用户"两人对话。只有架构级决策才启动合议。

### 教训 3：包拯审计揭露了三个泡沫

包拯的红方审计发现：
- NCD/压缩率范式区分力不足（AUC < 0.7）
- 反编译哈希线因反编译器输出差异 40%+ 应暂缓
- LLM-as-judge 是循环论证

**经验**：不要被"看起来很酷"的技术迷住。审计官的价值在于说"这个不行"。

**对 openLLM 的启示**：每做完一个模块，都要有"包拯"来审。不能自己审自己。

### 教训 4：编排管线（v4.0→v5.1）越改越复杂

研究编排从 v4.0 到 v5.1 经历了多次迭代，每次都在加新功能（子产情报、IKO 商业分析、四轨并行），但管线越来越重，维护成本越来越高。

**经验**：功能不是越多越好。**每加一个功能，先问"没有它行不行"**。

**对 openLLM 的启示**：openLLM 只有四根骨头（Iam/Soul/记忆/技能/约束）。每加一个组件，先问"没有它行不行"。不行才加。

### 教训 5：理论研究和代码实现的时间分配严重失衡

ITA 的理论研究产出丰富（200+ 篇 wiki 文档），但代码实现只完成了方案C 的最小验证。

**经验**：研究和实现应该是 **60:40**，不是 **90:10**。

**对 openLLM 的启示**：从今天开始，代码实现占 60%，理论研究占 40%。

## 三、ITA 对 openLLM 的直接遗产

| ITA 遗产 | openLLM 如何继承 |
|----------|-----------------|
| 编码假设（代码→向量→执行恢复） | Δ胶囊的记忆压缩机制 |
| 五人合议 | 重大决策的审议流程 |
| 包拯审计 | 每个模块的红方审计 |
| PAL 规划方法 | 项目管理的标准流程 |
| peer-review | 代码/设计的同行评议 |
| 长编→定本研究法 | FATA 的研究方法论 |
| 军规十条 | 代码质量标准 |

---

## 四、ITA 的遗憾

1. **没有把编码假设变成产品** — 60% 执行等价还不够，需要 90%+
2. **没有完成跨学科融合** — 意图压缩四层论还是理论，没有工程化
3. **没有建立持续的代码实现节奏** — 研究太多，代码太少

**openLLM 要弥补的**：这三条遗憾就是 openLLM 的 P0 任务。
